# From local workflows to a personal agent platform

This is a proposal for review. The first release should let someone start a run in one project, open the dashboard in another, and recover the same run after a crash. The four shared workflows come next. Chat, desktop, the hosted service and mobile all build on the same local engine.

## Build and review order

Each numbered item below can be reviewed as one pull request (PR). Keep each phase on its own branch. Land its slices in order and review the phase before starting the next one. For a behavior change, run the existing suite, add a failing test first, then run the changed tests and the suite again. Use fake agents, clocks and providers for routine tests. Report skipped checks and failed live trials by name.

### How a step reaches Dictaria

Dictaria exposes a remote HTTP MCP server with OAuth. A user-scoped HTTP entry named `dictaria` was present in Claude Code on the machine checked. Its live account, scopes and tool names were not tested. Prefer a dedicated intake step using `harness:claude-code` with a profile that has only the read access needed for Dictaria. On a new machine, register the supplied endpoint with `claude mcp add --transport http --scope user dictaria <endpoint>` and complete the browser login via `/mcp`. Keep the endpoint and tokens in user configuration. The logged-in harness makes the MCP call. The later draft worker gets selected meeting data only. [Claude Code MCP setup](https://code.claude.com/docs/en/mcp)

Before shipping, use the actual ACP adapter and scheduled environment to list the available tools and read a single test meeting. Verify stable IDs, paging, expired access and the absence of write tools before enabling the schedule. If the adapter cannot load the server or enforce read access, use a small trusted local helper from a shell step. It should use an MCP client over HTTP with OAuth stored in the OS keychain and expose only list/read operations. A missing login or incomplete page must stop intake.
